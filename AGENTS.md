# Agent instructions

Canonical, tool-agnostic instructions for any coding agent working in this repository.

Isomer turns one typed `Composition` into React, HTML, SVG, PNG, Slack Block Kit, Markdown, and plain text. It owns the composition contract, primitive catalog, validation, and rendering; hosts own data, authorization, routing, and side effects.

Preserve the composition's meaning through each surface's documented adaptation and fallback, not identical layouts or uniform validation semantics. Isomer is not a host application, data-fetching service, authorization layer, or transport framework. Image formats are produced by an optional host-side backend, not by adding a rasterizer to the SDK or runtime.

## Change process and evidence

1. Establish observable inputs, outputs, failure behavior, and consumers from current code, docs, and tests. Derive routine expectations from those contracts; ask only for unresolved product decisions.
2. Keep schemas, inferred types, catalogs, examples, projections, normalization, and rendering coherent. Preserve defaults, transforms, fallback, diagnostics, and side effects unless intentionally changing them.
3. Use assertions that distinguish plausible wrong behavior at the relevant consumer boundary. Demonstrate the old defect fails when feasible; never claim an unperformed red/green run.
4. Apply checks to behavior the change could affect, including adjacent states and cleanup. Reuse sufficient existing coverage; do not add tests just to satisfy a checklist. Name limits' per-field or aggregate scope. Derive geometry, clipping, rounding, and rendering tolerances from existing contracts; ask only when the intended outcome remains a product decision.
5. Evaluators and gates need independently established passing and known-failing cases for changed rules. Expectations generated by the same logic are not independent evidence; inspect baseline changes.
6. Update canonical docs and affected derivatives together. Verify review suggestions against the contract rather than accepting them automatically.

Report exact commands/results and meaningful untested risks. Distinguish source, browser, rendered-artifact, and installed-consumer evidence.

## Package map

The runtime lives in `packages/isomer-runtime` under `assemble/`, `registry/`, and `surfaces/`. Stage barrels there are hand-maintained the same way as the SDK's.

`packages/isomer-primitives-slides` is the in-repo reference pack. Its `src/registry.ts` and `src/body_node.ts` are hand-maintained the same way, and `src/registry.test.ts` fails when they drift. Its docs live in `packages/isomer-primitives-slides/docs/`. Primitive packs for Kibana iterate in that repo.

`packages/isomer-primitives-charts` is the chart pack, `"private": true` until the npm admin seeds `@elastic/isomer-primitives-charts` (TODO: remove `private`, and add it back to the Trusted Publisher list in RELEASING.md, once seeded; unseeded, its publish fails with `E404`): chart primitives on one shared core, `grid` and `unsupported`. Its `./schema` entry holds the contracts (schemas, node types, catalog entries and examples) and imports no renderer; `./scene` holds the Scene types renderers read and the `SceneRenderer` interface; formatting is internal to the resolver, from portable formats that are `Intl` options. Hosts and Kibana materializers build against it.

`packages/isomer-charts-elastic` is the Elastic Charts engine, `"private": true` while the charts pack is: a browser `SceneRenderer` that draws chart Scenes as Kibana draws its panels. It imports only the charts pack's `./scene` entry and keeps `@elastic/charts` and React as peers, so neither reaches the charts pack or its Hermes-safe entries.

`packages/isomer-primitives-vega` is the Vega pack, `"private": true` while the charts pack is: one `vega` primitive, a Vega or Vega-Lite spec with inline data drawn by the Vega runtime to an SVG string on every surface, with the charts pack's node conventions (`data`, provenance, `losses`, `ChartEvent`). It depends on the charts pack's `./schema` and `./resolve` entries, never the reverse. Its `./schema` entry reaches no Vega, so a client that cannot load Vega validates nodes with it. Kibana resolves a panel's queries and map tiles before Isomer sees a node; the pack never fetches.

`packages/isomer-image-takumi` renders the `snapshot` surface's output to PNG, SVG, or PDF. It depends on no isomer package — it declares the surface's result shape structurally.

`packages/isomer-evals` scores whether a model produces valid, well-chosen compositions from a pack's authoring context. It depends on the SDK's public API alone and runs with no credentials.

`packages/isomer-studio` is the `isomer-studio` CLI: `dev`, `build` and `check` over a consumer's `isomer-studio.config.ts`. Its `bin` runs the CommonJS build, which loads Vite with `import()`; it ships its browser app prebuilt in `lib/app` and keeps React at 18 until EUI allows 19. `dev` runs on Vite and hot-updates a changed config in place; `build` stays on esbuild. `pnpm studio:dev` runs the CLI from source against the root `isomer-studio.config.ts`, which gathers the in-repo packs with `images: false`. `pnpm test:browser` and `scripts/check_studio_consumer.js` drive it in Chromium.

`packages/isomer-agent-tools` turns any runtime into transport-neutral agent tools, resources, and a `compose` prompt. It declares the runtime structurally and depends on the SDK alone; hosts bring the transport, and it must never reach `@modelcontextprotocol/sdk`, which `scripts/check_module_graph.js` enforces.

## Release posture

Every package under `packages/` without `"private": true` publishes, at one version, through the release workflow: `@elastic/isomer-sdk` and `@elastic/isomer-runtime` are what a host installs, takumi is a host-side rasterizer, the Elastic Charts engine (private while the charts pack is) is what browser hosts draw charts with, the charts pack (private until seeded on npm) is what Kibana and the render service share, the Vega pack (private while the charts pack is) draws Kibana's Vega panels beside it, and the Studio is the CLI a pack installs to browse and check its primitives. The slides pack is an exemplar to copy and stays private; evals is a harness run from this repository and stays private; agent-tools is private until its API settles. A published package never lists a private one in `dependencies` or `peerDependencies`, which `scripts/check_pack_consumer.js` enforces. Do not raise publication, registry access, or dependency licensing as a constraint when planning work in this repository.

## Verify your work

```sh
pnpm verify
```

That is the complete local gate before a PR, except for prose-only changes below. `pnpm verify:fast` (build, typecheck, lint, license check, tests) is the iteration loop, not a substitute. Report unrelated failures rather than papering over them.

For prose-only changes, follow [Contributing's documentation checks](CONTRIBUTING.md#prose-only-changes) instead of the full gate, including before a PR. CI still runs `pnpm verify`.

## Conventions

- Conventional commits. `feat:` and `fix:` are release-driving.
- License headers are the Elastic License 2.0 block, enforced by ESLint (`license-header/header`). Use `pnpm lint:fix` rather than inserting them by hand. `.yml`/`.yaml` headers are hand-maintained.
- Brands use `Symbol.for`, never bare `Symbol()`.
- `IsomerError` is identified by `name` and `code`, never `instanceof`. `CompositionValidationError` is identified by `name`, `code`, and `errors`.
- Stage barrels (`packages/isomer-sdk/src/<stage>/index.ts`) are hand-maintained. When you add or remove an export from a module, update the barrel in the same commit. TypeScript enforces correctness; keeping them alphabetically sorted keeps diffs readable.
- `src/entries/*` are hand-curated on purpose: which names reach which subpath is what keeps `react-dom/server` off the root entry.
- `zod` is a peer dependency. Do not add it to `dependencies`.
- The sdk must not import the runtime.
- No tsconfig `paths`. Internal resolution is `workspace:*`: a package compiles against its dependencies' built declarations, so `pnpm -r` builds in dependency order.
- Each package builds as `elastic/eui`'s packages do: `tsc` emits ESM for bundlers to `lib/esm`, Babel emits CommonJS to `lib/cjs`, and `tsc` emits declarations beside it; Node consumers `require` the CommonJS build.
- After adding or changing a dependency, run `pnpm licenses:report` and include the updated `THIRD_PARTY_LICENSES.md` and `NOTICE.txt`.
- Narrative docs live in each package's `docs/`. Root `docs/` is the docs-builder assembler (landing page and OKF map); do not author package pages there. Its package folders are committed copies, because Elastic Internal Docs (Codex) clones and builds `docs/` as committed: run `pnpm docs:assemble` and commit the result whenever package docs change, and CI fails with `pnpm docs:check` when they drift. Preview with `pnpm docs:dev`.
- `.okf/isomer` keeps agent-facing detail the package docs don't cover; a concept the docs cover points to them instead of restating them. Put what a human reader needs in the package docs. When a change alters detail a concept keeps, update that concept and run `pnpm okf:check` and `pnpm okf:index`.
- `.okf/**` is excluded from markdown and Prettier formatting because `okf index` owns generated index formatting.
- Keep comments short. Do not narrate decisions that git history already records.
- A pack holds no rendered value of its own: every number, length, ratio, and glyph it draws has one authoring source in its theme ([Before you add a value](packages/isomer-primitives-slides/docs/primitives.md#before-you-add-a-value-one-source-per-rendered-value)).
- There is no per-primitive `snapshot` renderer. The `snapshot` surface dispatches to `react` and is handed the pack's stylesheet; do not reintroduce a second tree authored for image layout.
- The pack stylesheet does not reach inside an inline `<svg>`. Anything drawn there needs a literal `fill` / `stroke` alongside its class ([Drawing inside an `svg`](packages/isomer-primitives-slides/docs/primitives.md#drawing-inside-an-svg)).
